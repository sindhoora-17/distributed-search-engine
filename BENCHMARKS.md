# Benchmarks

## Methodology

- Corpus generated by `scripts/make_dataset.py` with a fixed seed for reproducibility.
- The benchmark lists the corpus once and partitions files **round-robin into N disjoint slices**, one per client thread.
- Each client indexes only its assigned slice, so total work stays constant as client count changes. This isolates the effect of client concurrency instead of multiplying the workload.
- Timing covers connect → stream assigned documents → server acknowledgement across all clients, measured with `System.nanoTime()`.
- Server and clients ran on the same machine, so the results measure concurrent-client scaling rather than cross-network performance.

## How to reproduce

```bash
cd app-java && mvn clean package
python3 ../scripts/make_dataset.py ../datasets/bench 2000 1500
# start the server, then:
java -cp target/app-java-1.0-SNAPSHOT.jar \
  com.sindhoora.distributedsearch.FileRetrievalBenchmark localhost 50051 <N> ../datasets/bench
```

## Recorded results

The recorded run used a generated corpus of 2,000 files (~23 MB total):

| Clients (N) | Corpus size | Index time (s) | Throughput (MB/s) |
|-------------|-------------|----------------|-------------------|
| 1           | 2,000 files | 1.061          | 21.66             |
| 2           | 2,000 files | 0.762          | 30.17             |
| 4           | 2,000 files | 0.665          | 34.56             |
| 8           | 2,000 files | 0.701          | 32.76             |

Throughput improves by about **1.6× from 1 to 4 clients**, then plateaus and slightly regresses at 8. The single central server merging all client streams becomes the bottleneck; beyond roughly four concurrent clients, contention in the shared merge path outweighs the benefit of additional clients.

A natural next step would be to shard the index across multiple server nodes so merge work can scale horizontally.

> These are single recorded runs per client count. For a more rigorous performance study, repeat each configuration several times and report medians and variance. The purpose here is to demonstrate the scaling shape and identify the central merge bottleneck, not to present production-grade performance numbers.
